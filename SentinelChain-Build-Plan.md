Team Turtle | 2nd NextGen Hackathon 2026 | Theme: Cybersecurity for the Future

This document is written to be handed directly to Antigravity as a build spec. It covers architecture, exact folder structure, data models, API contracts, the 4-layer pipeline logic, Claude prompts, and a day-by-day task split across all four teammates.

---

## 1. What We're Building (recap)

**Input:** a `package.json`/`package-lock.json`, or a single npm package name.
**Output:** a color-coded dependency risk map (0–100 score per package) with a plain-English AI explanation, generated by actually running each package in an isolated sandbox rather than just pattern-matching its source.

**4-Layer Pipeline:**
1. **Ingestion Layer** — resolve the dependency tree, queue each package
2. **Sandbox Execution Layer** — install + run each package in an isolated Docker container, capture real runtime behavior
3. **Static Analysis Layer** — typosquat detection, obfuscated eval/base64 chains, new-maintainer flags
4. **AI Scoring Layer** — Claude API turns sandbox + static findings into a 0–100 risk score + explanation

## 4. Data Models

**ScanResult (MongoDB)**
```json
{
  "_id": "scanId",
  "input": "package.json | packageName",
  "createdAt": "ISODate",
  "status": "queued | running | complete | error",
  "dependencyTree": [{ "name": "axios", "version": "1.7.2", "depth": 0 }],
  "results": [
    {
      "package": "axios@1.7.2",
      "riskScore": 82,
      "riskLevel": "critical | high | medium | low",
      "explanation": "string from Claude",
      "sandboxFindings": { "networkCalls": [], "fileWrites": [], "envAccess": [], "spawnedProcesses": [] },
      "staticFindings": { "typosquatScore": 0.02, "obfuscationHits": [], "newMaintainer": false },
      "cached": false
    }
  ]
}
```

**PackageCache (Redis key + Mongo backing store)**
Key: `pkg:{name}@{version}` → cached `results[i]` object above, TTL configurable (e.g. 7 days) so re-scans are instant, matching the "Caching by package@version" feature in the deck.

## 5. The 4 Layers — Implementation Detail

### Layer 1 — Ingestion
- Accept either an uploaded `package.json`/`package-lock.json` or a single package name typed in.
- Use `npm ls --all --json` (on a temp install) or parse the lockfile directly to get the **full resolved tree**, not just top-level deps — this is what makes the "dependency risk propagation" visual possible.
- For each unique `name@version`, check Redis/Mongo cache first. Only queue **uncached** packages into BullMQ.
- Push one BullMQ job per uncached package.

### Layer 2 — Sandbox Execution
- `Dockerfile.sandbox`: minimal Node image, **no outbound network by default** (`--network=none`), a non-root user, and a monitoring wrapper.
- Approach for capturing behavior without deep kernel instrumentation (fastest path for a 2-day hackathon):
  - Wrap `npm install <pkg>` and any `postinstall`/`preinstall` scripts with **`strace`** (or `dtrace` fallback) to log syscalls — filter for `execve`, `connect`, `open`/`openat` on sensitive paths (`~/.ssh`, `~/.aws`, `/etc/passwd`), and `write`.
  - For network calls specifically: run the container with `--network=<monitored-bridge>` and sniff with `tcpdump` inside, or use a simple proxy (`mitmproxy`/`http-mitm-proxy`) as the container's only route out, logging every request attempted (even if blocked).
  - Capture: file writes outside the install dir, spawned child processes, env var reads (`process.env` access can be caught by monkey-patching in a wrapper `--require` script), and any network connection attempts.
  - Hard timeout per package (e.g. 30s) — kill and mark `sandboxFindings.timedOut: true` if exceeded.
  - Output a structured JSON log per package.

### Layer 3 — Static Analysis
- **Typosquat detection:** Levenshtein/Damerau-Levenshtein distance between the package name and the top ~5,000 npm package names by download count; flag distance ≤ 2.
- **Obfuscation detection:** regex + lightweight AST walk (via `acorn` or `esprima`) over all `.js` files in the package for `eval(`, `Function(`, `atob(`/`Buffer.from(..., 'base64')` chains, and unusually long minified single-line files.
- **Metadata flags:** pull from npm registry API — maintainer account age, days since last version bump vs. this version's jump size, whether this version was published by a *different* maintainer than prior versions (classic account-takeover signal — matches the axios/node-ipc incidents in the deck).

### Layer 4 — AI Scoring (Claude API)
- `promptBuilder.js` assembles one structured prompt per package combining sandbox + static findings.
- Ask Claude for **strict JSON output** (score, level, explanation, top 3 red flags) so `scoreParser.js` can parse reliably — see prompt template below.
- Batch or parallelize calls across packages via the BullMQ worker concurrency setting.

**Prompt template (system + user):**
```
System: You are a software supply-chain security analyst. You will be given
structured sandbox and static-analysis findings for one npm package. Score
its risk from 0-100 and explain why in plain English for a developer with
no security background. Respond ONLY with JSON matching this schema:
{ "riskScore": number, "riskLevel": "low"|"medium"|"high"|"critical",
  "explanation": string, "redFlags": string[] }

User: Package: {name}@{version}
Sandbox findings: {sandboxFindings JSON}
Static findings: {staticFindings JSON}
Registry metadata: {maintainer age, version jump, publish gap}
```

## 6. API Contract (Backend ↔ Frontend)

- `POST /api/scan` — body: `{ packageJson }` or `{ packageName }` → returns `{ scanId }`
- `GET /api/scan/:scanId` — returns current `ScanResult` (poll every 1–2s, or upgrade to a WebSocket/SSE stream if time allows — nice demo touch for "watch the dependency tree render with live risk scores")
- `GET /api/health` — trivial liveness check

## 7. Frontend Plan

- **UploadPanel** — drag-drop `package.json` or type a package name.
- **DependencyTree** — force-directed or radial tree, nodes colored by risk (green/yellow/orange/red), sized by depth/impact. This is the single most important visual for the demo and the "risk propagation" pitch point — prioritize it.
- **PackageDrilldown** — clicking a node shows: risk score, Claude's explanation, the raw sandbox trace (network calls, file writes, spawned processes), and static flags.
- **ScanProgress** — live "N of M packages scanned" bar while the queue drains.

## 10. Build Order for Antigravity (concrete sequence)

1. Scaffold repo structure above; `docker-compose.yml` wiring Redis + MongoDB + backend + frontend.
2. Build `sandbox/Dockerfile.sandbox` + `runContainer.js` — get **one** package installing inside an isolated container with `strace`/network logging working end-to-end before anything else. This is the highest-risk, most novel piece — de-risk it first.
3. Build `ingestion/resolveTree.js` to walk a real `package.json`.
4. Build the static analysis scanners (self-contained, no external dependencies on sandbox output — parallelizable with step 2).
5. Wire BullMQ: one job per package, worker runs sandbox → static → AI scoring in sequence, writes to Mongo, caches in Redis.
6. Build `ai-scoring/` against the Claude API using the prompt template above; validate JSON parsing with a few real packages (try one known-clean package and one you deliberately make suspicious).
7. Build the malicious demo package in `test-packages/` — something that does a plausible-looking bad thing (e.g. reads `process.env`, attempts an outbound POST to a webhook, writes outside its install dir) so the sandbox has something real to catch.
8. Build the Express routes + polling/SSE endpoint.
9. Build the React frontend, starting with `DependencyTree` since it's the visual centerpiece.
10. Integration pass + demo rehearsal using the exact 3-step script above.

## 11. Key Risks to Flag Early

- **Sandbox monitoring is the hardest and most novel part** — don't let it slip to Day 2. If `strace`-based syscall capture proves too slow to get working, fall back to a simpler version: run install with `--ignore-scripts` off, monkey-patch Node's `fs`, `child_process`, and `net` modules via a `--require` preload script injected into the container, and log every call. Less "real" than syscall tracing but far faster to build and still demonstrates true runtime behavior monitoring (the key differentiator vs. static-only tools).
- **Time-box the AI scoring prompt** — get JSON parsing reliable early; a malformed response mid-demo is the most visible failure mode.
- **Keep the malicious test package simple and safe** — it should *look* dangerous to the sandbox (network call, env read, file write) without actually doing anything harmful, since it'll run inside your own demo environment.
